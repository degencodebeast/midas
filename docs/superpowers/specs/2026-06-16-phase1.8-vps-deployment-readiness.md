# Phase 1.8 — VPS Deployment Readiness

> **Why:** Post-Phase-1.7 review confirmed the branch is functionally strong, but not yet self-contained or operationally ready for a clean VPS deployment. Three verified gaps remain: (1) the scanner dependency is still a sibling editable path, so `midas` cannot boot from a fresh checkout alone; (2) the live path still runs with `CmcContextAdapter(client=None)`, so production CMC context is not wired; (3) ERC-8004 identity resolution depends on `bnbagent_sdk`, but that runtime dependency is not declared in `midas` and a clean install currently degrades silently to `agent_id=None`. This phase makes the runtime self-contained, documents the deploy contract, and packages a safe VPS rollout path.

> **Outcome:** A fresh VPS can install the agent from this repo plus explicitly documented external repos/services, run the loop under supervision, serve the API/dashboard, and expose a reproducible paper → testnet → live rollout procedure.

---

## 1. Purpose & Scope

This specification defines the requirements for making `midas` deployable on a VPS in a repeatable, production-minded way.

In scope:
- self-contained runtime/install contract
- scanner dependency strategy
- ERC-8004 runtime dependency strategy
- real CMC live wiring
- process model for `run`, `serve`, and `web`
- secrets/env contract
- persistence contract for `.magic_agent/*`
- supervisor + reverse-proxy packaging
- deployment documentation and smoke checks

Out of scope:
- redesigning the trading strategy
- changing the bounded-advisor safety model
- building a Kubernetes stack
- multi-node scaling
- database migration from JSON files to external storage

---

## 2. Definitions

- **VPS**: Virtual Private Server running Linux, managed over SSH.
- **Self-contained install**: A fresh machine can install and start the agent using only documented dependencies and setup steps, without relying on undeclared local machine state.
- **Scanner**: The sibling `trading-scanner` project that provides `magic_scanner.scan.scan_symbols`.
- **CMC**: CoinMarketCap Agent Hub / API-backed context source used to derive `ContextSnapshot`.
- **ERC-8004 identity**: On-chain agent identity resolved through the BNB agent SDK wrapper.
- **Paper mode**: Safe execution mode using `PaperExecutor`, no real funds.
- **Testnet mode**: Real external services, no production funds.
- **Live mode**: Real external services and real funds.

---

## 3. Verified Starting Point

The following are already present and should be preserved:

- `magic-agent run` drives the poll loop.
- `magic-agent serve` exposes `/api/status` and `/api/decisions`.
- `web/` renders the read-only dashboard from the API.
- Cross-process state flows through:
  - `.magic_agent/status.json`
  - `.magic_agent/decisions.jsonl`
- The bounded advisor remains:
  - off by default
  - key-gated
  - `None` on failure
  - clamp-only
- Policy remains fail-closed.

This phase must not weaken those properties.

## 4. Requirements

### 4.1 Runtime Packaging

- **REQ-001**: A fresh VPS install must not depend on an undeclared sibling path existing accidentally.
- **REQ-002**: The scanner dependency strategy must be made explicit and executable. Acceptable options:
  - package `magic-scanner` as an installable dependency from a documented source, or
  - define a documented multi-repo deployment layout that checks out `trading-scanner` beside `midas` and treats that as part of the required deploy shape.
- **REQ-003**: The chosen scanner strategy must be validated by a clean-install smoke path, not just local dev assumptions.
- **REQ-004**: Any runtime import used by the live path must be declared or explicitly provisioned in the deploy instructions.
- **REQ-005**: `bnbagent_sdk` support must be made honest and reproducible:
  - if required for identity, it must be installable from the deploy instructions;
  - if optional, the docs must say identity is optional and the UI will show `unregistered`.

### 4.2 Live Context Wiring

- **REQ-006**: The live path must stop hardcoding `CmcContextAdapter(client=None)` if the product claim is that live context comes from CMC.
- **REQ-007**: A real CMC client seam must be wired into `_cmd_run()` through environment/config.
- **REQ-008**: If no CMC credentials are configured, the system may degrade to `status="unavailable"`, but that fallback must be documented as a deploy-mode choice, not an invisible default claim.

### 4.3 Deployment Contract

- **REQ-009**: The deployment docs must define the exact processes required for a single-node VPS deployment.
- **REQ-010**: The deployment docs must define the shared working-directory requirement for:
  - `.magic_agent/status.json`
  - `.magic_agent/decisions.jsonl`
- **REQ-011**: The deployment docs must define all required and optional environment variables, grouped by subsystem:
  - core runtime
  - Aster
  - LLM advisor
  - ERC-8004 identity
  - CMC
  - dashboard/API

### 4.4 Operational Packaging

- **REQ-012**: Provide a supervised process model suitable for a VPS. Preferred default: `systemd`.
- **REQ-013**: Provide unit/service definitions for:
  - `magic-agent run`
  - `magic-agent serve`
  - dashboard web process
- **REQ-014**: Provide a reverse-proxy recommendation and example configuration for exposing the dashboard/API safely.
- **REQ-015**: The API should bind privately by default behind the proxy unless there is a documented reason not to.

### 4.5 Rollout Safety

- **REQ-016**: The deployment runbook must prescribe a staged rollout:
  - paper
  - testnet
  - small-notional live
- **REQ-017**: The runbook must include a smoke checklist proving:
  - loop starts
  - status snapshot updates
  - decision log writes
  - API responds
  - dashboard reads the API
  - advisor key-gating behaves correctly
  - Aster path is verified in the chosen environment
- **REQ-018**: The runbook must include safe failure expectations and rollback steps.

### 4.6 Constraints

- **CON-001**: Do not redesign the strategy or scanner semantics in this phase.
- **CON-002**: Do not weaken the clamp-only LLM authority boundary.
- **CON-003**: Do not add hidden runtime dependencies that are absent from docs.
- **CON-004**: Do not claim sponsor integrations are live if they still degrade to placeholders or unavailable mode.

## 5. Interfaces & Data Contracts

### 5.1 Required Runtime Commands

The deployment contract must support these commands:

```bash
magic-agent run [flags]
magic-agent serve --host 127.0.0.1 --port 8000
```

And the dashboard:

```bash
npm run build
npm run start
```

### 5.2 Expected Shared Local State

The following paths are required to persist between `run` and `serve`:

```text
.magic_agent/status.json
.magic_agent/decisions.jsonl
```

### 5.3 Environment Contract

The deployment docs must define, at minimum, the meaning of:

```text
ASTER_PRIVATE_KEY
ASTER_WALLET_ADDRESS
ASTER_TESTNET

MAGIC_AGENT_LLM_API_KEY
MAGIC_AGENT_LLM_MODEL

MAGIC_AGENT_ERC8004_URI
MAGIC_AGENT_ERC8004_RPC
MAGIC_AGENT_ERC8004_KEY

NEXT_PUBLIC_API_BASE
```

And any CMC env vars added by this phase.

### 5.4 UI/API Topology

Recommended topology:

```text
Browser
  -> Reverse proxy (TLS)
     -> Next.js web process
     -> FastAPI serve process (/api/*)

magic-agent run
  -> writes .magic_agent/status.json
  -> writes .magic_agent/decisions.jsonl

magic-agent serve
  -> reads same files
```

## 6. Acceptance Criteria

- **AC-001**: Given a fresh VPS following the documented install steps, when the operator installs dependencies, then `magic-agent run --executor paper` starts without relying on undeclared local machine state.
- **AC-002**: Given a fresh VPS following the documented install steps, when `magic-agent serve` starts, then `/api/status` and `/api/decisions` respond successfully.
- **AC-003**: Given the dashboard is configured with `NEXT_PUBLIC_API_BASE`, when `npm run start` is run behind the documented proxy, then the UI loads and reads the live API.
- **AC-004**: Given no CMC credentials are configured, when the agent runs, then the system degrades honestly and the deploy docs describe that behavior.
- **AC-005**: Given CMC credentials are configured, when the agent runs, then the live path uses a real CMC client rather than `client=None`.
- **AC-006**: Given ERC-8004 identity is configured, when the agent starts, then the dependency required to resolve it is installable from the documented setup and `agent_id` is surfaced honestly.
- **AC-007**: Given ERC-8004 identity is not configured, when the agent starts, then the dashboard shows `unregistered` and the docs describe that as an acceptable mode.
- **AC-008**: Given the repo on a fresh machine, when the deployment smoke test is executed, then the operator can prove the paper rollout end to end.
- **AC-009**: Given the rollout runbook, when the operator advances from paper to testnet to live, then each step includes a checklist and explicit go/no-go criteria.

## 9. Rationale & Context

The current branch is close to demo-ready, but “merge-ready” is not the same as “fresh-VPS deployable.” The remaining issues are not aesthetic:

- sibling editable dependency assumptions break clean installs
- undeclared runtime imports break reproducibility
- hardcoded unavailable/live-degraded integrations weaken product truthfulness

This phase keeps the bounded-agent design intact while making operational claims honest and reproducible.

## 11. Examples & Edge Cases

### Example A — Honest degraded deployment

- VPS has no CMC credentials
- ERC-8004 env vars absent
- advisor key absent

Expected:
- loop runs in deterministic mode
- context status becomes `unavailable`
- dashboard shows `unregistered`
- no crash, no fake identity, no fake live CMC claim

### Example B — Clean paper deployment

- paper executor
- advisor disabled
- `serve` running
- dashboard pointed at API

Expected:
- status snapshot updates
- decision log updates
- API responds
- dashboard renders real values

### Example C — Live deployment preconditions

- Aster credentials present
- scanner available
- CMC configured or explicitly accepted as degraded
- operator has completed paper and testnet smoke steps

Expected:
- live rollout is deliberate, not accidental
